IT setup · Connect on Harrow servers

Connection method: approved department Google Drive documents → Gemini File Search → answers with citations in Harrow Ask. Opening a NotebookLM link does not connect its answers. NotebookLM sources are refreshed separately.

Hosting plan: Harrow hosts the website, API and application database on its own infrastructure. Google Drive and Gemini remain external services used for documents and answers. The instructions below describe the target setup; the current hosting adapter and storage must be migrated before this build will run independently on Harrow servers.

  1. Prepare Harrow hosting and migrate the backend. Assign an HTTPS address on a school-controlled domain and a staging address. Serve the public/ files through the school's web server and run the API in a maintained Node.js runtime compatible with Node 22 or later, managed by IT's service or container platform. Adapt the existing Fetch Request/Response handler to the school's HTTP server and change the frontend API URL from /.netlify/functions/ask to a same-origin school endpoint such as /api/ask, preserving the existing route query and authentication. Replace the current @netlify/blobs storage with a school-managed persistent database adapter for the department catalogue, source manifests and resumable sync jobs. Preserve atomic conditional writes, revision checks and sync leases; separate staging and production data. Carry across the existing security headers, configure HTTPS proxy handling and request limits, and protect administration using staff roles. Configure backups and restore checks. Copying the website files alone will not enable live answers.
  2. Prepare the Google project and Drive access. In a school-approved Google Cloud project, enable the Google Drive API and create a dedicated service account. Give its email Viewer access to the approved department source folder. The app uses Drive read-only access without domain-wide delegation. Use an IT-managed service-account PEM key for the server configuration below; if school policy prevents service-account keys or external folder sharing, this pilot needs an alternative approved authentication method before use.
  3. Configure the answer service. Enable access to the Gemini API in an approved project, configure an API key, and select a model that supports File Search with generateContent. Confirm quota and school approval for processing these documents. The app requires an explicit model ID; a NotebookLM subscription or link is not a Gemini API credential.
  4. Configure staff sign-in. Create a Google OAuth client of type Web application. Configure the consent screen for the school and add the exact Harrow production HTTPS origin to Authorised JavaScript origins, plus the approved staging origin. Use the actual addresses assigned by IT, without paths or trailing slashes. This app uses the Google Identity Services JavaScript callback; there is no app OAuth redirect endpoint to invent. School server access controls are separate from school sign-in and staff authorisation within Harrow Ask.
  5. Configure the school API service. Store the variables below in IT's secret manager or protected service environment, accessible only to the API process. Configure staging separately. Restart or redeploy the school API service after changes. Permit outbound HTTPS from that service to oauth2.googleapis.com, www.googleapis.com and generativelanguage.googleapis.com. Staff browsers must also reach accounts.google.com for sign-in and Google Drive for source links. Keep keys out of source code, frontend variables and chat messages.

If the warning remains: confirm all variables are available to the school API process, restart it after changes, inspect school API and reverse-proxy logs without exposing secrets, then check folder sharing, model support, quota and whether an approved, enabled department has successfully synced. แผนการติดตั้ง: Harrow เป็นผู้ดูแลเว็บไซต์ API และฐานข้อมูลแอปพลิเคชันบนระบบของโรงเรียน ส่วน Google Drive และ Gemini ยังคงเป็นบริการภายนอกสำหรับเอกสารและคำตอบ ขั้นตอนนี้อธิบายระบบที่ต้องการติดตั้ง โดยต้องปรับส่วนเชื่อมต่อระบบโฮสต์และระบบจัดเก็บข้อมูลปัจจุบันก่อน จึงจะใช้งานบนเซิร์ฟเวอร์ Harrow ได้โดยไม่พึ่งระบบโฮสต์เดิม

  1. เตรียมเซิร์ฟเวอร์ Harrow และย้ายระบบเบื้องหลัง กำหนดที่อยู่ HTTPS บนโดเมนที่โรงเรียนควบคุมและที่อยู่สำหรับระบบทดสอบ (staging) ให้เว็บเซิร์ฟเวอร์ของโรงเรียนให้บริการไฟล์ใน public/ และรัน API ด้วย Node.js รุ่นที่ยังได้รับการดูแลและรองรับ Node 22 ขึ้นไป ผ่านระบบบริการหรือคอนเทนเนอร์ที่ IT ดูแล ปรับตัวจัดการ Fetch Request/Response เดิมให้ทำงานกับ HTTP server ของโรงเรียน และเปลี่ยน URL ของ API ในส่วนหน้าจาก /.netlify/functions/ask เป็น endpoint บน origin เดียวกัน เช่น /api/ask โดยคงพารามิเตอร์ route และการตรวจสอบสิทธิ์ไว้ แทนที่ @netlify/blobs ด้วยตัวเชื่อมต่อฐานข้อมูลถาวรที่โรงเรียนดูแล เพื่อเก็บรายการแผนก รายการและเวอร์ชันเอกสาร และงานซิงค์ที่ดำเนินการต่อได้ ต้องคงการเขียนข้อมูลแบบมีเงื่อนไขและเป็นอะตอม การตรวจสอบ revision และกลไก sync lease เพื่อป้องกันงานซ้ำ แยกข้อมูลทดสอบออกจากข้อมูลจริง ย้าย security headers เดิม ตั้งค่าการทำงานผ่าน HTTPS proxy และข้อจำกัดของคำขอ รวมถึงจำกัดส่วนผู้ดูแลตามบทบาทบุคลากร จัดให้มีการสำรองข้อมูลและทดสอบการกู้คืน การคัดลอกเฉพาะไฟล์เว็บไซต์จะยังไม่ทำให้ระบบตอบคำถามจริงได้
  2. เตรียม Google project และสิทธิ์เข้าถึง Drive ใช้ Google Cloud project ที่โรงเรียนอนุมัติ เปิดใช้ Google Drive API และสร้าง service account เฉพาะสำหรับระบบนี้ ให้สิทธิ์ Viewer แก่อีเมลของ service account ในโฟลเดอร์เอกสารที่ได้รับอนุมัติ ระบบอ่านข้อมูล Drive เท่านั้นและไม่ใช้ domain-wide delegation ใช้คีย์ PEM ของ service account ที่ IT ดูแลในการตั้งค่าเซิร์ฟเวอร์ด้านล่าง หากนโยบายโรงเรียนไม่อนุญาตคีย์ service account หรือการแชร์โฟลเดอร์กับบัญชีภายนอก ต้องจัดหาวิธียืนยันตัวตนทางเลือกที่ได้รับอนุมัติก่อนใช้งานระบบนำร่องนี้
  3. ตั้งค่าบริการตอบคำถาม เปิดใช้ Gemini API ใน project ที่ได้รับอนุมัติ ตั้งค่า API key และเลือกโมเดลที่รองรับ File Search ผ่าน generateContent ตรวจสอบโควตาและการอนุมัติของโรงเรียนสำหรับการประมวลผลเอกสาร ระบบต้องระบุ model ID อย่างชัดเจน การสมัครใช้ NotebookLM หรือลิงก์สมุดบันทึกไม่ใช่ข้อมูลรับรองสำหรับ Gemini API
  4. ตั้งค่าการเข้าสู่ระบบของบุคลากร สร้าง Google OAuth client ประเภท Web application ตั้งค่าหน้าจอขอความยินยอมสำหรับโรงเรียน และเพิ่ม HTTPS origin ของระบบใช้งานจริง Harrow รวมถึง origin ของระบบทดสอบที่ได้รับอนุมัติใน Authorised JavaScript origins ใช้ที่อยู่จริงที่ IT กำหนด โดยไม่ใส่ path หรือเครื่องหมาย / ปิดท้าย แอปใช้ JavaScript callback ของ Google Identity Services จึงไม่ต้องสร้าง OAuth redirect endpoint เพิ่ม การควบคุมการเข้าถึงเซิร์ฟเวอร์โรงเรียนแยกจากการเข้าสู่ระบบและสิทธิ์บุคลากรใน Harrow Ask
  5. ตั้งค่าบริการ API ของโรงเรียน เก็บตัวแปรด้านล่างในระบบจัดการความลับของ IT หรือ environment ของบริการที่ได้รับการป้องกัน ให้เฉพาะโปรเซส API เข้าถึงได้ ตั้งค่าระบบทดสอบแยกต่างหาก และ restart หรือ deploy บริการ API ใหม่หลังแก้ไข อนุญาต HTTPS ขาออกจากบริการไปยัง oauth2.googleapis.com, www.googleapis.com และ generativelanguage.googleapis.com เบราว์เซอร์ของบุคลากรต้องเข้าถึง accounts.google.com เพื่อเข้าสู่ระบบ และ Google Drive เพื่อเปิดเอกสารอ้างอิงได้ ห้ามใส่คีย์ใน source code ตัวแปรฝั่งหน้าเว็บ หรือข้อความแชต

  1. กำหนดผู้รับผิดชอบและซิงค์ LS CCA เข้าสู่ Harrow Ask ด้วยบัญชีผู้ดูแลที่อยู่ในรายการอนุญาต เปิด Department notebooks แก้ไข Lower School CCA ระบุอีเมลโรงเรียนของหัวหน้าแผนกและลิงก์โฟลเดอร์ Drive อนุมัติเอกสารให้บุคลากรที่ได้รับอนุญาตทุกคนอ่านได้ แล้วบันทึก เลือก Sync department และรอ Sync complete ตรวจสอบจำนวนเอกสาร เวอร์ชัน และเวลาซิงค์ครั้งล่าสุดที่สำเร็จ เปิดใช้งานแผนกเมื่อพร้อมให้บุคลากรใช้ เก็บเฉพาะไฟล์ที่ระบบรองรับไว้ในโฟลเดอร์โดยตรง ห้ามมีโฟลเดอร์ย่อยหรือ shortcut จำกัด 40 ไฟล์ และ 8 MB ต่อไฟล์ การนำเข้าตารางรวมทุก worksheet แม้ชีตที่ซ่อนไว้ จึงต้องใช้สำเนาสำหรับบุคลากรที่ลบชีตลับออกแล้ว
  2. ตรวจสอบก่อนเปิดใช้กับบุคลากร ทดสอบการเข้าสู่ระบบด้วยบัญชีโรงเรียน คำถาม LS CCA จริง การอ้างอิงเอกสารต้นฉบับ คำถามที่เอกสารไม่รองรับ คำตอบภาษาไทย และถ้อยคำเกี่ยวกับร่างนโยบาย ตรวจสอบว่าหัวหน้าแผนกซิงค์แผนกของตนได้ แต่เปลี่ยนแปลงแผนกอื่นไม่ได้ แก้ไขหรือลบเอกสารทดสอบ ซิงค์ใหม่ และตรวจสอบว่าคำตอบใช้ชุดข้อมูลใหม่ หากซิงค์ล้มเหลว ระบบยังใช้ชุดข้อมูลจากการซิงค์ครั้งล่าสุดที่สำเร็จ หากต้องถอนเอกสารด่วน ให้พักการใช้งานหรือเก็บแผนกเข้าคลัง

หน้าที่ในการดูแลต่อเนื่อง: หัวหน้าแผนกอัปเดตเอกสารต้นฉบับที่ได้รับอนุมัติและกด Sync department รวมถึงอัปเดต NotebookLM แยกต่างหาก IT ตรวจสอบโควตาและลบ Gemini File Search stores ที่ไม่ได้ใช้ ระบบนำร่องสร้างดัชนีใหม่ทุกครั้งที่ซิงค์ และยังไม่ลบดัชนีเก่าโดยอัตโนมัติ

หากข้อความเตือนยังปรากฏ: ตรวจสอบว่าโปรเซส API ของโรงเรียนเข้าถึงตัวแปรทั้งหมดได้ restart หลังแก้ไข ตรวจสอบ log ของ API และ reverse proxy โดยไม่เปิดเผยข้อมูลลับ จากนั้นตรวจสอบสิทธิ์แชร์โฟลเดอร์ การรองรับของโมเดล โควตา และการซิงค์ที่สำเร็จของแผนกที่ได้รับอนุมัติและเปิดใช้งานแล้ว การตั้งค่าบริการสำเร็จเพียงอย่างเดียวไม่ได้หมายความว่าได้นำเข้าเอกสารแล้ว
